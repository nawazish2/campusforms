# Database

Two migrations, applied in order. At this scale the simplest route is the
Supabase dashboard's SQL editor — paste each file and run it. The CLI
(`supabase db push`) works too but wants Docker for its local stack.

| File | What it does |
|---|---|
| `0001_init.sql` | `forms` and `responses`, the anonymity and counter triggers, and every RLS policy |
| `0002_restrict_signups.sql` | Rejects sign-ups from outside the university domain — **edit `allowed_domain` before running it** |

## Then, in the dashboard

1. **Authentication → Providers → Google**: enable it, and paste the client id
   and secret from a Google Cloud OAuth client.
2. **Authentication → URL Configuration**: add your deployed origin and
   `http://localhost:3000` to the redirect allow-list.
3. **Project Settings → API**: copy the URL and anon key into `.env.local`
   (see `.env.local.example`).

## Things the schema decides, on purpose

- **`questions` and `answers` are `jsonb`.** Nothing ever queries a question
  on its own — the builder rewrites the whole array per edit and every summary
  iterates it in JS — so a form saves as one upsert and question ids, which
  answers are keyed by, stay stable for free.
- **`deadline` is `text`, not `timestamptz`.** It holds two shapes with
  different meanings: `2026-09-25` (end of that local day) and
  `2026-09-25T18:00` (a local wall clock). A timestamp column collapses them.
- **Anyone can read any form, in any status.** `/f/[id]` needs draft and
  closed forms to exist in order to explain why they aren't accepting
  responses. Nothing in a form definition is confidential.
- **Only the organizer can read responses.** Which is why `forms` carries a
  trigger-maintained `response_count`: the public pages show "6 responses"
  without being able to see one.
- **Response ids are generated by the client.** A submitter can't read their
  row back, and the confirmation screen shows them a reference number.
- **There is no `submitted_by` and no IP column,** and a trigger clears the
  name and email on any response to an anonymous form. Anonymity that only
  exists in the UI isn't anonymity.

## After applying, check these three things

```sql
select gen_form_id();                    -- hex id, no error about pgcrypto
select tgname from pg_trigger            -- did 0002's trigger survive?
  where tgname = 'enforce_university_domain_on_signup';
```

Then insert a response to an anonymous form using the anon key with a name
filled in, read it back as the owner, and confirm `respondent_name` is null.
That single check proves RLS, the trigger and anonymity are all live.

## Still to do before this is live

- **Deadline enforcement on write.** The insert policy checks
  `status = 'open'`; the deadline is checked in the app. Move it into a
  trigger before you rely on a closing time.
- **Server-side answer validation.** `validateFill` runs in the browser only.
- **Seed data.** There is none: a fresh database starts empty, so `/browse`
  is blank until an organizer publishes a form. Seeding would mean writing
  `supabase/seed.sql` against a real `owner_id`, which only exists after the
  first sign-in.
